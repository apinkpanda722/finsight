# UX 가이드: 유저 획득과 온보딩 전환

## 목적
이 문서는 Figma의 UI 디자인 원칙 7가지([참고](https://www.figma.com/ko-kr/resource-library/ui-design-principles/))를 Finsight의 실제 화면과 사용자 여정에 맞게 구체화한 가이드다. 색상·타이포·radius 같은 시각 토큰은 `DESIGN.md`와 `.claude/skills/finsight-design-system/`을 따르고, 이 문서는 그 토큰을 **어디에, 왜, 어떤 순서로** 쓸지에 집중한다. 목표는 두 가지다.

1. 랜딩 페이지에서의 유저 획득(방문 → 가입 전환)
2. 가입부터 "아하 모먼트"(첫 인사이트 확인)까지 이탈 없는 단계별 전환

## 왜 이 문서가 필요한가
Finsight는 금융 데이터를 다루는 조용하고 단정적인 톤을 이미 확정했다(`DESIGN.md`) — 악센트 컬러 1개, 이모지 없음, 긴급성 문구 없음. 화려한 전환 트릭을 쓸 수 없는 만큼, 계층 구조·점진적 공개·근접성 같은 "구조적" 원칙에 더 크게 의존해야 유저를 잃지 않는다.

## 1. Finsight 유저 여정 전체 지도

```
랜딩 도착 → 샘플 미리보기로 가치 확인 → 회원가입 → 이메일 인증 대기
  → 이메일 링크 클릭 → 로그인 → 빈 대시보드(첫 업로드 유도)
  → CSV 업로드(동의 → 업로드 → 처리 상태) → 첫 인사이트 확인(아하 모먼트)
  → Free 3개월 제한 인지 → Pro 전환
```

아래 모든 원칙 적용은 이 여정을 기준으로 한다. 단계 사이 "다음으로 갈 이유"가 명확할수록 이탈이 줄어든다.

## 2. Figma 7원칙 → Finsight 적용

### 2.1 계층 구조 (Visual Hierarchy)
사용자가 주요 정보를 먼저 인식하고 덜 중요한 요소와 구분하도록 글꼴 크기·굵기·색상 대비·간격으로 순서를 만든다.

- 랜딩 히어로는 헤드라인(80px, `font-heading`) → 서브카피(16px, `on-dark-soft`) → CTA 순으로 이미 이 순서를 따른다 — 유지.
- 악센트 컬러가 하나뿐이므로 금액 강조는 색이 아니라 **JetBrains Mono + 크기**로만 만든다(`SamplePreview`의 `financial-number text-3xl` 패턴).
- 대시보드 개요에서 "이번 달 총지출" 같은 헤드라인 숫자가 화면에서 가장 큰 텍스트여야 한다. 카테고리 목록·차트는 그보다 작게.

체크리스트
- [ ] 한 화면에서 시선을 끄는 요소가 2개 이상 경쟁하지 않는가
- [ ] 스크롤 없이 보이는 영역에 핵심 가치 제안 + 1차 CTA가 있는가

### 2.2 점진적 공개 (Progressive Disclosure)
여러 단계 프로세스는 한 화면에 몰아넣지 않고 단계별로 나누되, 사용자가 진행 상황과 남은 단계를 알 수 있게 한다.

- 회원가입 폼은 이메일+비밀번호 2필드뿐이다(계좌 이름 등 부가 정보는 첫 업로드 시점에 물어봄) — 좋은 패턴, 유지.
- 업로드 모달은 `select → uploading → pending → processing → completed/failed` 단계 전이를 한 컴포넌트가 순차적으로 보여주고, 각 단계에서 필요한 정보만(파일 선택 시엔 계좌 선택 + 동의 체크박스만) 노출한다 — 유지.
- **개선 여지**: 이메일 인증 대기 화면(`/login`의 `view === "verify"`)에 "1/2단계" 같은 진행 표시가 없다. 사용자는 지금 전체 가입 과정 중 어디에 있는지 알 수 없다. 짧은 진행 텍스트나 단계 인디케이터 추가를 검토할 가치가 있다.

체크리스트
- [ ] 한 화면의 질문/입력이 3개를 넘지 않는가
- [ ] 다단계 흐름이면 지금 몇 단계인지 알 수 있는가

### 2.3 일관성 (Consistency)
디자인 시스템을 통해 패턴을 일관되게 유지해 사용자가 인터페이스에 익숙해지도록 한다. 기존 패턴에서 벗어날 땐 타당한 근거가 필요하다.

- 카드 radius(24px), 버튼 radius(pill), hover 인터랙션(`-translate-y-1 scale-[1.02]`)이 랜딩·대시보드·샘플 프리뷰 전역에서 반복 사용된다 — 새 컴포넌트도 이 패턴을 재사용한다.
- 참고: 이 hover 클래스 문자열이 `page.tsx`와 `sample-preview.tsx`에 각각 로컬 상수로 중복 정의돼 있다. 지금은 값이 같아 문제가 없지만, 한쪽만 고치면 화면 간 인터랙션이 갈라질 수 있으니 공유 상수화를 고려해볼 만하다(이 문서 범위 밖의 코드 정리 제안).

체크리스트
- [ ] 새 버튼/카드가 기존 radius·hover·타이포 토큰을 그대로 쓰는가
- [ ] 기존 패턴과 다르게 갈 경우 이유를 설명할 수 있는가

### 2.4 대비 (Contrast)
중요한 콘텐츠·액션으로 주의를 끌기 위해 전략적으로만 사용한다. 보조 액션은 낮은 대비로 혼란을 줄인다.

- 악센트가 하나뿐이므로 "이 버튼이 중요하다"는 신호는 색이 아니라 **버튼 variant**로 준다. 주 CTA(가입하기, Pro로 시작)는 `default`(Deep Azure 배경), 보조 액션(요금제 보기, 로그인)은 `outline`/`ghost` — 현재 랜딩 페이지가 이 규칙을 잘 지키고 있다.
- 위험 액션(계좌·명세서 삭제)은 색상 대비 대신 `destructive` variant + 인라인 확인 인터랙션(`ConfirmDelete`, 별도 모달 아님)을 쓴다 — 이미 설계에 반영됨.

체크리스트
- [ ] 화면에 `default` variant 버튼이 2개 이상 동시에 있지 않은가(주장은 하나만)
- [ ] 파괴적 액션에 확인 인터랙션이 있는가

### 2.5 접근성 (Accessibility)
색상·명도 조정, 대체 텍스트, 키보드 탐색, 전경/배경 대비를 통해 시각 장애가 있는 사용자도 접근 가능하게 한다.

- 금액 텍스트(JetBrains Mono)와 배경의 대비가 라이트/다크 두 배경 모두에서 WCAG AA(4.5:1) 이상인지 확인한다.
- 업로드 진행률바·상태뱃지는 색만으로 상태를 구분하지 않고 텍스트 라벨을 항상 병기한다(예: "처리 중" 텍스트 + 색).
- CSV 업로드는 드래그앤드롭만 제공하지 말고, 키보드로 접근 가능한 파일 선택 버튼을 항상 함께 둔다.

체크리스트
- [ ] 상태(성공/실패/처리중)를 색 없이 텍스트만으로도 구분할 수 있는가
- [ ] 인터랙티브 요소가 키보드만으로 도달 가능한가

### 2.6 근접성 (Proximity)
서로 관련 있는 요소는 함께 배치해 자연스러운 연관성을 인식시키고, 오조작 위험이 있는 액션은 분리한다.

- 업로드 모달에서 계좌 선택과 파일 선택은 붙여서, 동의 체크박스는 그 아래 별도 그룹으로, 업로드 시작 버튼은 동의 체크박스 바로 아래에 두어 "무엇에 동의하고 무엇을 실행하는지" 헷갈리지 않게 한다.
- 명세서 목록에서 삭제 버튼은 각 행 안에 두되 재시도 버튼과는 시각적으로 분리한다(오조작 방지) — `StatementRow`가 이미 이 패턴을 따른다.

체크리스트
- [ ] 관련 필드/버튼이 시각적으로 인접해 있는가
- [ ] 되돌릴 수 없는 액션이 자주 쓰는 액션 바로 옆에 붙어있지 않은가

### 2.7 정렬 (Alignment)
강력한 그리드로 질서와 균형을 잡아 가독성과 예측 가능성을 높인다.

- `max-w-(--container-max)` 컨테이너가 랜딩·대시보드 전역에 일관 적용된다 — 새 섹션도 이 폭을 벗어나지 않는다.
- 카드 그리드는 항상 4px 배수 간격(24px)을 유지한다.

체크리스트
- [ ] 새 섹션이 기존 컨테이너 폭·그리드 gap을 그대로 쓰는가

## 3. 유저 획득 설계 (랜딩 페이지)

### 3.1 가치 제안은 스크롤 없이 답한다
헤드라인 "지출을 있는 그대로, 이해하기 쉽게."는 기능이 아니라 결과를 말한다 — 유지. 서브카피가 "무엇을 업로드하면 무엇을 얻는지"(CSV → 카테고리별 지출 + 월별 추이)를 한 문장으로 답한다 — 유지.

### 3.2 신뢰는 '증명'이 아니라 '체험'으로 만든다
초기 유저 기반이 없는 단계에서는 로고 월·후기 같은 사회적 증명을 쓸 수 없다. 대신 `SamplePreview`("가입 전에 분석 결과를 먼저 확인하세요")가 실제 제품 경험을 그대로 보여주며 신뢰를 대체한다 — Figma의 "점진적 공개" 원칙을 획득 단계로 앞당겨 적용한 패턴이며, 계속 투자할 가치가 있다.

**개선 여지**: 샘플 프리뷰 섹션 자체에는 CTA가 없다(현재 CTA는 히어로와 최하단 요금제 섹션뿐). 관심이 가장 높은 지점(샘플 결과를 막 확인한 순간)에 "내 명세서로 확인하기" 같은 2차 CTA를 추가하면 이탈 없이 전환시킬 여지가 있다.

### 3.3 CTA는 한 번에 하나의 주장만 한다
히어로의 CTA 2개(주 CTA "무료로 시작하기" + 보조 "요금제 보기")는 variant 대비(default vs outline)로 적절히 구분된다 — 3개 이상으로 늘리지 않는다.

**발견된 마찰 지점**: `StartButton`은 `/login`으로 연결되는데 `/login` 페이지의 초기 `view`는 항상 `"login"`이다. "무료로 시작하기"를 누른 사용자는 가입 의도로 클릭했음에도 로그인 폼을 먼저 보고 "회원가입"을 한 번 더 눌러야 한다 — CTA 라벨이 약속한 화면과 실제 다음 화면이 어긋나는 계층 구조/일관성 위반이다. 쿼리 파라미터(예: `/login?view=signup`)로 시작 뷰를 지정하는 방식을 검토할 가치가 있다.

### 3.4 요금제 섹션은 선택 마찰을 줄인다
카드 2개(Free/Pro)만 두고 Pro를 dark card로 시각 강조하는 대비 구조는 유지한다. 티어를 3개 이상으로 늘리면 의사결정 피로가 늘어나므로 지양한다.

## 4. 온보딩 단계별 전환 상태

| 단계 | 화면 | 적용 원칙 | 현재 상태 |
|---|---|---|---|
| 1. 도착 | 랜딩 | 계층 구조 + 대비 | 반영됨 |
| 2. 가치 확인 | `SamplePreview` | 점진적 공개(가입 전 체험) | 반영됨, CTA 보강 여지(3.2) |
| 3. 가입 | `/login` signup view | 최소 마찰(2필드) | 반영됨, 진입 경로 마찰 있음(3.3) |
| 4. 이메일 인증 대기 | verify view | 진행 상태 인지 | 진행 표시 없음(2.2) |
| 5. 로그인 | login view + `justVerified` 배너 | 직전 행동에 대한 피드백 | 반영됨 |
| 6. 빈 대시보드 | `EmptyDashboard` | 다음 행동 명확화(단일 CTA) | 반영됨 — "CSV 업로드하기" 단일 CTA |
| 7. 첫 업로드 | 업로드 모달 | 근접성 + 명시적 동의 | 반영됨(동의, 상태 전이) |
| 8. 아하 모먼트 | 대시보드 인사이트 | 계층 구조(총지출이 가장 큰 숫자) | 화면 완성 후 재확인 필요 |
| 9. Free 제한 인지 → Pro 전환 | 잠긴 히스토리 배너 | 대비(업그레이드 CTA는 튀지 않되 명확) | PRD·ADR-007에 설계 반영 |

추가로 확인된 마찰: `EmptyDashboard`의 "CSV 업로드하기"는 `/uploads`로만 이동시키고, 업로드 모달(`uploadOpen`)은 기본값이 닫혀 있어 사용자가 도착 후 다시 한번 열기 버튼을 눌러야 한다. 6→7 전환에서 `/uploads?upload=1` 같은 신호로 도착 시 모달을 자동으로 열어주면 첫 업로드까지의 클릭 수를 줄일 수 있다.

## 5. 측정: 이 설계가 통하는지 알아야 한다
Figma 원칙 문서가 강조하듯 정기적인 사용자 테스트로 문제를 조기에 발견해야 한다. Finsight 규모에서는 정식 A/B 인프라 대신 최소한 단계별 전환 이벤트만이라도 남긴다:

```
landing_view → signup_started → signup_completed → email_verified
  → first_login → first_upload_started → first_upload_completed
  → first_insight_viewed → upgrade_clicked → upgrade_completed
```

이 이벤트들은 현재 코드베이스에 계측되어 있지 않다. 별도 analytics provider 도입은 이 문서 범위 밖이며, 도입 시 `vercel:marketplace` 스킬로 provider를 먼저 선정한다.

## 6. 새 화면/컴포넌트 작업 시 체크리스트
- [ ] 스크롤 없이 보이는 영역에 핵심 메시지 + CTA 1개가 있는가
- [ ] 이 화면에서 사용자가 다음에 뭘 해야 하는지 한 문장으로 답할 수 있는가
- [ ] CTA 라벨이 약속한 것과 실제 다음 화면이 일치하는가
- [ ] 다단계 흐름이면 진행 상태를 알 수 있는가
- [ ] 1차 계층을 색이 아니라 크기·굵기·간격으로 표현했는가
- [ ] 위험 액션에 `destructive` variant + 확인 인터랙션을 썼는가
- [ ] 관련 있는 필드/버튼이 시각적으로 인접해 있는가
- [ ] 상태(성공/실패/처리중)를 색 없이 텍스트만으로도 알 수 있는가
